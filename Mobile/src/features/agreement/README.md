# Угоди PassBy / Sprint 2

Модуль використовує поточну React-оболонку, `screen` / `setScreen` та наявні
`Brand`, `PageHeader`, `Footer`, `Button`, `Field` і toast. Нові стилі обмежено
класами `ag-*`; наявні глобальні CSS-файли не змінено.

## Запуск демонстрації

У `Mobile/`: `npm run dev`, потім `http://localhost:5173/?demo=agreement`
(фактичний порт дивіться у виводі Vite). На звичайних екранах у dev-режимі
також є кнопка «Демо · угода». Авторизація основного застосунку не змінюється.

У панелі «Демо · угода» можна:

- обрати замовника або кур’єра;
- почати з порожнього чату, чернетки будь-якої сторони, укладеної,
  переданої кур’єру або скасованої угоди;
- імітувати передавання лише після укладання угоди;
- спричинити помилку наступного запиту та повторити дію;
- оновити дані, зокрема для перевірки конфлікту двох відкритих вкладок.

Перемикання учасника та передавання — лише засоби демонстрації. У production
демонстраційна точка входу вимкнена; її можна явно ввімкнути під час збірки
через `VITE_AGREEMENT_DEMO=true`. Параметр URL сам по собі її не вмикає.

Дані зберігаються окремо у `passby:agreement-demo:v1`. Скасовані угоди та історія
їхніх умов зберігаються; нова чернетка не видаляє стару. Скидання демосценарію
замінює тільки ці демонстраційні дані. Облікові записи застосунку не зачіпаються.

## Поведінка

Створення / зміна чернетки означає згоду автора з поточною редакцією.
Інша сторона може запропонувати нову ціну або погодити поточну редакцію.
Власна пропозиція не погоджується повторно. Незмінений чернетковий запис не
зберігається як нова редакція. Після прийняття другою стороною одразу фіксується
`agreedAtUtc` та `AwaitingHandover`; додаткової серверної стадії «готова до
укладання» немає. У фінальному вікні обидва індикатори зелені, редагування
недоступне. Укладання не підтверджує оплату, холд, передавання або доставлення.

Скасувати можна `Draft` і `AwaitingHandover`, лише до передавання кур’єру та
після підтвердження в окремому діалозі. Після `InTransit` звичайне скасування
недоступне. У mock-моделі скасування має доменний статус `Failed` та окремий
`cancelledAtUtc`; адаптер реального API повинен відрізняти скасування від інших
причин невиконання.

Призначені фізичні відправник та отримувач мають окремі ID й імена. Вони не
є автоматично замовником і не є додатковими сторонами погодження.

Грошові значення обробляються цілими копійками (`rewardKopecks`),
комісія — 20%, округлення до найближчої копійки. Мінімум — 100 грн.
UI замовника містить винагороду, комісію та підсумок; UI кур’єра — винагороду.

## Межа інтеграції з backend

`services/mockAgreementService.js` є асинхронним адаптером. Компоненти не
викликають HTTP і не покладаються на вигадані URL. Потрібні погоджені контракти:

| Операція адаптера | Потрібні дані / гарантії backend |
| --- | --- |
| `getCurrent` | Контекст Mutual, обидва Order, учасники, призначені відправник/отримувач, актуальна угода або null |
| `getDetails` | Доступні поточному учаснику умови та достовірний стан виконання |
| `createDraft` | ID контексту, ціна; поточний користувач із JWT; авторство пропозиції та початкова редакція |
| `updateDraft` | ID угоди, ціна, ExpectedTermsRevision; актуальна редакція у відповіді |
| `accept` | ID угоди, ExpectedTermsRevision; атомарне прийняття лише іншою стороною |
| `cancel` | ID угоди, перевірка прав і фактичного стану передавання; збереження історії |

У відповідях потрібні `collaborativeDealId`, `interactionContextId`,
`dealExecutionStatusCode`, `termsRevision`, `lastProposedByUserId`,
`agreedAtUtc`, дані обох сторін, окремі `senderUserId` / `receiverUserId`,
маршрут із назвами місць, посилка та винагорода. Визначення погодження
відповідає SQL `vCollaborativeDealDetails`: `delivererAccepted`,
`deliveryRequesterAccepted`, `isAgreed` є похідними значеннями.
`rewardKopecks` потрібно перетворювати на серверний
`finalPriceWithoutCommission` на межі API з узгодженим форматом decimal.
Комісія та підсумок зараз обчислюються для UI; реальна інтеграція повинна
використовувати актуальну політику ціноутворення сервера.

Потрібні визначені помилки прав доступу, конфлікту редакцій, недопустимого
стану та валідації; після конфлікту UI перечитує дані й вимагає повторного
перегляду умов. Повторні кліки блокуються на час запиту. Генерація секретів,
авторизація, конкурентні транзакції та ідемпотентність реальних операцій
залишаються відповідальністю backend. Чат у цьому модулі локальний і має бути
замінений / підключений до окремого модуля повідомлень.

## Розбіжності вимог

- Міграція `PassBy_Migration_2026-11-24.sql` підтримує чернетки й прийняття
  актуальної редакції, але `FailCollaborativeDeal` дозволяє скасування тільки
  `Draft`. Нове правило тимліда щодо `AwaitingHandover` виконано лише в mock.
- Figma показує «Готова до укладення» та додаткове «Укласти угоду». За SQL і
  актуальними вимогами друге погодження одразу укладає угоду. UI показує
  «Угоду укладено», без додаткової фіктивної серверної стадії.
- SQL дозволяє редагування координат і призначених учасників у Draft;
  за поточним UI-завданням маршрут заблоковано, учасники надходять із контексту.
- SQL угоди не має окремих погоджених строків передавання / доставлення;
  SRS згадує строки як частину плану. Поля й контракти потребують погодження.
- Правило SRS щодо мінімуму 100 грн і комісії 20% застосовано у frontend;
  backend повинен гарантувати ті самі правила незалежно від клієнта.
- У SRS суперечать один одному спільний адаптивний клієнт та Web лише для
  підтримки/адміністрації. Модуль працює в браузері через Mobile і Capacitor;
  окремий Web-клієнт не змінено.

## Перевірки

`npm run test:agreement` — Node.js tests, без нових залежностей.
`npm run build` — звичайна production-збірка.

Візуальні референси — надані PNG, MCP Figma недоступний. Додано обов’язкові
поля призначених учасників, редакцію, замовлення, фінансовий підсумок замовника,
статуси погодження в картці чату та кнопку скасування в деталях. Через це
картки/діалоги вищі за оригінальні зображення; довгі діалоги прокручуються.
Використано наявний шрифтовий стек Inter / Segoe UI / Arial без завантаження
нового шрифту; без Inter у системі можливі відмінності метрик. Нові прості
лінійні SVG-іконки відтворюють надані PNG; точні вектори потрібного фрейму MCP
не отримано. Логотип та базові компоненти взято з наявного застосунку.
